# /screen-inventory — 화면 인벤토리

이 사이트는 한 코드베이스 안에 수학(기존)·영어단어·TOEFL·학생관리 4개 서브시스템이 같이
자란 구조라, 화면이 늘어나면서 "누가 왜 만들었는지 잊힌 화면"이 생기기 쉽다. 아래를
**순서대로** 수행해 지금 실제로 존재하는 화면 전체를 한 장으로 파악한다. 중간에 판단이
필요하면 멈추지 말고 합리적으로 판단해 계속 진행하되, 무엇을 어떻게 판단했는지 최종 보고에 적는다.

## 1. 화면 목록 수집

`src/app` 아래 `page.tsx`와 `layout.tsx`를 전부 찾는다(Glob `src/app/**/page.tsx`,
`src/app/**/layout.tsx`). 파일 경로를 Next.js 라우트 경로로 변환한다
(`src/app/admin/students/[id]/page.tsx` → `/admin/students/[id]`, 라우트 그룹 `(name)`은
경로에서 빠진다는 점도 반영). `layout.tsx`는 그 자체가 화면은 아니지만 **권한 가드가
layout에서 한 번만 걸리는 경우**(예: `admin/toefl/layout.tsx`)가 있으므로, 그 아래 모든
page의 "역할" 판단에 쓸 근거로 같이 읽어둔다 — 표의 별도 행으로 넣지 않는다.

## 2. 화면별 정보 채우기

각 page.tsx에 대해 아래 5개 열을 채운다. 파일을 열어 실제로 읽고 판단할 것 — 파일명만
보고 추측하지 않는다.

- **경로**: 1단계에서 구한 라우트 경로.
- **역할**: 파일이 실제로 확인하는 가드를 근거로 넷 중 하나를 고른다. **이 열에는 정확히
  아래 네 글자 중 하나만 적는다 — 괄호·물결표로 세부사항을 덧붙이지 않는다**
  (예: `관리자(owner/admin)`, `관리자~조교`, `학생(수강생)`처럼 쓰지 않는다. "어떤 등급의
  관리자인지", "왜 리다이렉트인지" 같은 세부사항은 "화면 목적" 열이나 "비고" 열에 적는다).
  이렇게 값을 네 개로 고정해야 8단계에서 이 열 값 그대로 그룹핑해 셀 수 있다 — 세부사항을
  섞으면 "관리자"가 여러 변종 문자열로 쪼개져 자동 집계가 깨진다(실제로 2026-08-27 3차
  검토에서 이 실수로 역할별 합계가 어긋난 적이 있다 — 같은 실수를 반복하지 않는다).
  - **관리자**: `src/lib/roles.ts`의 `isStaff`/`canManageSite`/`canManageStudents`/
    `canViewGrades`/`canAssignRoles` 중 하나를 쓰거나, `/admin/**` 경로 아래 있으면서
    실제로 관리자 세션을 요구하는 화면. 등급 차이(owner만/전 직원 등)는 화면 목적에 적는다.
  - **학부모**: 로그인 세션이 아니라 URL의 토큰(`[token]` 등)으로 접근을 결정하는 화면
    (예: `report/[token]`).
  - **학생**: 로그인 세션은 요구하지만 관리자 가드는 없는 화면.
  - **공개**: 로그인 여부와 무관하게 접근 가능한 화면(랜딩, 로그인/가입, 샘플 미리보기,
    리다이렉트 전용 화면 등). 리다이렉트뿐이라는 사실은 화면 목적/비고에 적는다.
  - `/admin/**` 아래 있는데 코드에 실제 가드 호출이 없으면(또는 반대로 학생 경로인데
    관리자 가드가 있으면) 이건 판단이 아니라 **6단계 "역할 불일치"** 후보로 따로 표시한다.
- **화면 목적**: 파일을 읽고 한 줄로 요약(주석이나 spec 인용이 있으면 참고하되, 실제
  JSX가 무엇을 렌더링·제출하는지로 판단한다).
- **진입 경로**: 이 라우트로 연결되는 곳을 찾는다. 아래를 모두 시도한다.
  - `Grep -e "href=[\"'\`].*<경로 앞부분>" src` (동적 세그먼트는 `[id]` 같은 부분을 빼고
    접두사로 검색 — 예: `/admin/students/[id]`면 `/admin/students/`로 검색 후 뒤에 변수가
    붙는지 확인)
  - `router.push(`, `redirect(`, `NextResponse.redirect(` 안에 같은 경로 문자열
  - 미들웨어(`src/middleware.ts`)가 이 경로로 강제 리다이렉트하는지
  - 발견한 곳은 "어느 화면/코드에서" 형태로 적는다(예: "`/toefl` 랜딩의 Start 버튼",
    "세션만료 시 미들웨어 리다이렉트"). 위 방법으로 하나도 못 찾으면 **"(고아)"**로 적는다.
    단, `/`(홈), `/login`, `/signup`처럼 브라우저 주소창으로 직접 오는 게 정상인 진입점
    화면은 고아로 세지 않는다 — 왜 그런지 한 줄로 남긴다.
- **주요 액션 버튼**: 반드시 **지금 파일을 열어 실제 JSX의 `<button>`/`<Link>`/`<a>` 텍스트를
  읽어서** 3~5개만 뽑는다(순수 표시용 UI는 제외). 이전 실행 결과·기억·설명 문구에서 베끼지
  않는다 — 코드가 바뀌었으면 버튼도 바뀌었을 수 있다. 버튼이 사실상 없는 안내성 화면이면
  "(없음)".

## 3. 표 조립

아래 열 순서로 마크다운 표 하나에 전부 담는다(서브시스템별로 소제목 구분은 해도 되지만
표 자체는 하나로 이어져야 비교가 된다):

| 경로 | 역할 | 화면 목적 | 진입 경로 | 주요 액션 버튼 | 비고 |
|---|---|---|---|---|---|

"비고" 열에 4~6단계에서 찾은 태그(`고아(조치 필요)`, `고아(의도된 리다이렉트)`,
`중복 의심: <그룹명>`, `역할 불일치`)를 적는다. 여러 개면 쉼표로 이어 적는다. 해당 없으면 빈 칸.

## 4. 고아 판정

3단계 표에서 진입 경로가 "(고아)"인 행마다, 그 파일을 열어 본문이 사실상 `redirect(...)`
하나뿐인지(또는 마운트되자마자 `router.replace(...)`만 호출하는지) 확인해 둘 중 하나로
표시한다:

- **고아(의도된 리다이렉트)**: 화면 자체가 다른 곳으로 보내기만 하는 게 목적이라, 인바운드
  링크가 없는 게 오히려 정상이다(옛 북마크·외부 링크가 들어올 때만 쓰인다).
- **고아(조치 필요)**: 그 외 — 실제 UI가 있는데 아무도 연결하지 않는 화면. 지우거나,
  연결을 추가하거나, 왜 남겨뒀는지 확인이 필요한 진짜 문제.

"고아"라고만 쓰지 않는다 — 항상 둘 중 하나로 구체화한다.

## 5. 중복 의심 그룹핑

"화면 목적"이 비슷한 화면끼리 묶는다. 판단 기준:

- **진짜 중복 의심**: 같은 사용자층에게 같은 일을 시키는 화면이 두 개 이상 존재하는 경우
  (예: 시작 화면이 여러 번 재설계되며 옛 화면이 안 지워진 경우 — 실제로 이 프로젝트는
  8/18~19에 `/toefl`이 재설계되며 `/toefl/start`가 분리된 이력이 있으니 이 둘의 역할이
  지금도 겹치는지 실제로 읽고 확인할 것).
- **중복 아님(구조상 병렬)**: 같은 모양이지만 서브시스템이 달라 의도적으로 나란히 존재하는
  화면(예: `/admin/students/[id]`와 `/admin/toefl/students` — 학생 관리 축이 다름, 위
  `student-management-module`/`toefl-subsystem-plan` 메모에 이미 "축이 다르다"고 명시돼
  있음). 이런 경우는 중복 의심에 넣지 말고, 넣고 싶은 유혹이 들었다면 왜 아닌지 최종
  보고에 한 줄 남긴다.

그룹마다 짧은 그룹명을 정해 관련 행의 "비고"에 `중복 의심: <그룹명>`을 적고, 표 아래
"### 중복 의심 그룹" 절에 그룹별로 왜 비슷하다고 판단했는지 1~2문장 남긴다.

## 6. 역할 불일치 판정

아래 두 경우를 찾아 "비고"에 `역할 불일치`를 추가하고, 표 아래 "### 역할 불일치" 절에
파일:줄 근거와 함께 구체적으로 적는다:

- 학생/공개 경로 아래에 관리자 전용 동작(문항 승인, 역할 부여, 전체 학생 조회 등)이
  섞여 있는 경우.
- `/admin/**` 경로인데 실제 코드에 `isStaff`/`canManage*` 등 가드 호출이 전혀 없는 경우
  (미들웨어가 대신 막고 있는지 `src/middleware.ts`를 확인해서, 그것도 없으면 심각도를
  "가드 없음(보안 위험)"으로 표시).

## 7. 이전 스냅샷과 비교(삭제된 화면 찾기)

`review/screens_*.md`를 Glob해서 가장 최근에 수정된 파일을 찾는다(오늘 이미 한 번 실행했어도
상관없다 — 그 파일이 "이전 스냅샷"이다). 없으면 이 단계는 건너뛴다.

그 파일의 표에 있던 경로 목록을 뽑아, 1단계에서 새로 수집한 경로 목록과 비교한다. **이전엔
있었는데 지금은 없는 경로**(파일이 삭제됐거나 라우트가 바뀐 것)를 전부 적어둔다 — 이 목록은
9단계에서 쓴다. 지금 표에는 넣지 않는다(살아있는 화면만 표에 남긴다).

## 8. 저장 — 매번 새로 만든다

**중요: 이전 파일에 이어붙이지 않는다.** 오늘 날짜(로컬 시스템 날짜, `YYYYMMDD`)로
`review/screens_<YYYYMMDD>.md` 파일명을 정하고, 같은 이름의 파일이 이미 있어도(오늘 두 번째
실행이어도) **파일 전체를 지금 결과로 완전히 새로 쓴다** — "재실행 결과" 절을 위에 덧붙이는
식으로 예전 실행 내용을 남겨두지 않는다(예전 내용이 궁금하면 git 이력이나 7단계에서 읽은
이전 스냅샷 파일 자체를 보면 된다). `review/` 폴더가 없으면 만든다.

- **저장 직전 자가 점검**: "역할" 열에 실제로 나온 값을 전부 나열해본다. `관리자`/`학생`/`공개`/
  `학부모` 딱 4개만 있어야 한다. 다른 값이 하나라도 보이면(괄호·물결표가 섞인 변종 등) 저장을
  멈추고 2단계 규칙대로 표를 고친 뒤 다시 센다 — 고치지 않은 채로 "대략 이 정도"라고 반올림해서
  요약에 적지 않는다.
- **요약은 전부 3단계에서 조립한 표를 세어서 채운다 — 손으로 숫자를 적지 않는다:**
  ```
  # 화면 인벤토리 (<YYYY-MM-DD>)

  ## 요약
  - 전체 화면 수: <표의 행 수>개
  - 역할별: 공개 <N>개 · 학생 <N>개 · 관리자 <N>개 · 학부모 <N>개
    (표의 "역할" 열 값을 실제로 세어서 채운다 — 네 값의 합이 전체 화면 수와 같아야 한다)
  - 고아(조치 필요): <비고에 "고아(조치 필요)"가 있는 행 수>개
  - 고아(의도된 리다이렉트): <비고에 "고아(의도된 리다이렉트)"가 있는 행 수>개
  - 중복 의심: <비고에 "중복 의심"이 있는 행 수>개 화면 (<그룹 수>개 그룹)
  - 역할 불일치: <비고에 "역할 불일치"가 있는 행 수>개
  ```
- 그다음 3단계 표, 5단계 "### 중복 의심 그룹", 6단계 "### 역할 불일치" 순서로 이어붙인다.

## 9. 변경 이력

맨 아래에 "## 변경 이력" 절을 두고, 7단계에서 찾은 "삭제된 화면"을 한 줄씩 적는다(경로 +
알 수 있으면 왜/언제 없어졌는지 한 줄). 이번이 첫 실행이라 비교 대상이 없었으면
"이번이 첫 실행이라 비교 대상 없음"이라고 적는다. 삭제된 화면이 없으면 "변경 없음"이라고 적는다.

## 10. 완료 보고

사용자에게 보고: 저장된 파일 경로, 전체 화면 수, 역할별 개수, 고아(조치 필요)/고아(의도된
리다이렉트) 각각의 개수, 중복 의심 그룹 수(+화면 수), 역할 불일치 개수, 이번에 삭제된 것으로
확인된 화면이 있으면 그 목록. 역할 불일치가 "가드 없음(보안 위험)"으로 나온 게 있으면 반드시
맨 앞에 강조해서 보고한다.
